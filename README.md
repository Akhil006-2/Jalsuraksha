# JalSuraksha — Chennai Flood Watch

JalSuraksha is a development prototype for flood awareness in Chennai. It combines a static relative-susceptibility raster, a Chennai OpenStreetMap road graph, community-submitted observations, spatial/temporal corroboration, and prototype route comparison.

## Important limitations

- The XGBoost raster is a **relative susceptibility score**, not a calibrated probability or live flood observation.
- The raster covers only its study-area footprint, not all of Chennai.
- Route durations are rough mode-based estimates; there is no live traffic, closure, rainfall, water-level, or sensor feed.
- Community corroboration means the configured count of distinct reporter tokens was reached. Anonymous tokens cannot prove distinct human identities and can be abused.
- The responder token is development-grade. Do not expose this service publicly or use it for real emergency decisions without proper authentication, rate limiting, durable storage, audit logging, privacy/retention policy, operational validation, and trusted live data.
- OpenStreetMap tiles require attribution and use-policy compliance.

## Project layout

## Community corroboration policy

Initial configurable defaults in `app/config.py`:

- Radius: `JALSURAKSHA_CLUSTER_RADIUS_M=150`
- Recency window: `JALSURAKSHA_CLUSTER_WINDOW_MINUTES=120`
- Minimum distinct reporter tokens: `JALSURAKSHA_CLUSTER_MIN_REPORTERS=3`
- Report influence half-life: `JALSURAKSHA_REPORT_HALF_LIFE_MINUTES=60`

The cluster service groups recent active observations by geographic proximity. A cluster becomes `corroborated` only when it reaches the configured distinct-token threshold. The underlying individual report records remain in their own report lifecycle; the UI derives cluster corroboration from the cluster response. A public request cannot manually set a report status to `corroborated`. Only a responder token can set `verified` or `rejected`.

The reporter token is a pseudonymous client-generated UUID stored in local browser storage. It reduces accidental repeat counting in a browser but is **not a verified identity mechanism**; multiple tokens can be generated by one person, and shared browsers can share a token. Do not describe the threshold as proof of independent people.

## Map layers and routing

The frontend uses Leaflet and OpenStreetMap tiles, and requests a georeferenced transparent PNG from `/api/v1/susceptibility/overlay.png` plus WGS84 bounds from `/api/v1/susceptibility/bounds`. The overlay is limited to the raster footprint and can be hidden or have its opacity changed.

Route comparison returns candidate LineString geometries and a rough travel-time estimate based on travel mode. It applies static susceptibility and recent report influence as a prototype cost function. It does not prove any route is safe or currently passable.

## Uploads and storage

Photos are limited to JPEG, PNG, or WebP signatures and the configured maximum size. Local JSON and photo storage are suitable only for development; concurrent multi-process writes, durable backups, moderation, private image access, and retention/deletion controls need a production storage design.


## Hardening updates in this bundle

- Vite proxies `/api` to FastAPI during local development, avoiding the common `Failed to fetch`/CORS mismatch when opening the frontend on `localhost:5173`.
- Route candidates now expose per-route relative susceptibility, nearby active-report counts, corroborated hazard segment counts, and explicit caveats. The available rainfall dataset is city-wide rather than route-specific, so the API deliberately does not claim that a specific road had lower historical rainfall.
- Optional SQLite persistence is available for a single-instance deployment:
  - PowerShell: `$env:JALSURAKSHA_STORAGE_BACKEND = "sqlite"`
  - Optional database path: `$env:JALSURAKSHA_SQLITE_PATH = "data/reports/jalsuraksha.sqlite3"`
  - The default remains JSON for compatibility with the current tests and local setup. SQLite is not a substitute for managed PostgreSQL/PostGIS in a multi-instance production deployment.
- Status changes and report creation are written to an audit log (`data/reports/audit.jsonl` in JSON mode; `audit_log` table in SQLite mode).
- Uploaded photos are served with private/no-store headers and require the responder token. Do not use the default `responder-dev-key` outside local development; set `JALSURAKSHA_RESPONDER_TOKEN` to a strong secret.
- An experimental expansion script is included at `scripts/expand_susceptibility_to_chennai.py`. It intentionally refuses to create an output if the supplied DEM does not cover the full requested bounds. This archive currently contains only the N12E080 DEM tile, which does **not** cover all of metropolitan Chennai. Download and mosaic the required adjacent DEM tiles and obtain an authoritative Chennai/CMDA boundary before generating a citywide raster. Even after that, expanded output is spatial extrapolation from a model trained on a much smaller AOI and must not be represented as validated citywide prediction.

## Flood-first routing revision

The app now serves the OpenCity / Greater Chennai Corporation `Chennai Flows 100 Years Return Period` KML at `/api/v1/flood-hazards` and point classifications at `/api/v1/flood-hazards/at`. The frontend renders the mapped HIGH, MODERATE, and LOW polygons as a separately toggleable layer.

Route comparison now intersects road segments with the source polygons, removes mapped HIGH-hazard segments for the preferred A* pass, and only permits them as a warned fallback if no path avoiding those mapped HIGH zones exists in the selected routing corridor. A* uses straight-line distance as its heuristic; weighted edges cost at least their physical length, so the heuristic remains admissible. Further candidates are generated by rerunning A* with penalties on previously used edges. These are useful alternatives, not exhaustive mathematically optimal K-shortest paths.

The route explanations report counts of mapped HIGH/MODERATE/LOW and UNCLASSIFIED segments. Routes outside mapped polygons are UNCLASSIFIED, never called flood-free. Static flood hazard is a design scenario, not a complete historical flood inventory or live inundation feed. No result is a safety guarantee.

**Coverage and production status:** this layer only covers its source polygons. The existing susceptibility raster remains limited to its original study footprint; it has not been extrapolated into a claimed citywide prediction. Full production deployment still requires real-time water/closure feeds, a validated complete city road graph, authentication and rate limiting, secure photo storage, backups, monitoring, privacy/retention controls, and validation by local authorities. JSON storage remains the default as requested; use a single application process when relying on local JSON writes.
